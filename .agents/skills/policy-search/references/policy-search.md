# Cross-project policy search method

A topic-neutral, read-only procedure for finding rules across Wikimedia wikis. Use it with a topic recipe (for example, [AI policy search](ai-policy-search.md)) and the [evidence/reporting contract](evidence-and-change-reporting.md). A person or any agent can follow these files; no particular agent, model, local profile or installer is required. This procedure does not edit the source wikis or claim that searching every site discovers every relevant rule.

## Set the contract before collecting

Record the research question; included and excluded project families and sites; time window; page classes (adopted policy/guideline, other guidance, proposal, essay, information, discussion); the comparison catalogue, if any; search terminology and discovery routes; the intended audience; and how incomplete work will be labelled. Record whether the run is a first baseline, broad rediscovery or a narrower recheck. Agree who checks findings before a working note is shared. A recurring cadence is not permission to schedule or publish.

## Discover and verify

1. **Enumerate the approved corpus.** Use the [SiteMatrix API documentation](https://www.mediawiki.org/wiki/API:Sitematrix) to obtain site URLs and codes, including the special-project entries. Check whether sites such as multilingual Wikisource and Beta Wikiversity fall within the approved scope; these are examples to verify against the current matrix, not a fixed site list. Record the enumeration date, each included site and every exclusion (closed, inaccessible, out of scope or otherwise). Follow continuation if returned. The topic recipe decides which families are included; do not substitute a convenient list of large editions. Keep family, language and site ID distinct.
2. **Resolve each site's search space.** Inspect that site's [siteinfo namespace metadata](https://www.mediawiki.org/wiki/API:Siteinfo) before searching. Record the local projectspace namespace ID and name; do not assume the English namespace label or a universal namespace number. Some operative rules may live elsewhere, so document additional indexes and namespaces used.
3. **Search by multiple routes.** Use localized topic terms and aliases in the site's [search API](https://www.mediawiki.org/wiki/API:Search), including an explicit namespace and continuation. Search local policy/guideline indexes, categories, backlinks and relevant interwiki or sitelink leads where useful. Preserve the query/route for each candidate. Search hits and snippets are leads, not findings; a sparse result is not proof of absence.
4. **Check every candidate on its own wiki.** Retrieve the current canonical page and relevant section, following redirects while retaining the discovered title. Record host/site ID, page ID, namespace, canonical title, URL/anchor, latest revision ID and timestamp, local status evidence (such as banner/template and applicable local index), and the **original-language operative passage**. Use [revision metadata](https://www.mediawiki.org/wiki/API:Revisions) or a revision/diff link to support temporal claims. A copied excerpt, linked translation, category or third-party catalogue label cannot establish this page's status. Preserve translation uncertainty for human review.
5. **Classify without collapsing categories.** Distinguish adopted policy/guideline, non-binding guidance, proposal/draft, essay/information page, historical or superseded rule, discussion, and unverified candidate. The topic recipe specifies which classes enter the main results. An operative provision on a general rule page can qualify even when the title omits the topic; retain the parent and precise section. Incidental examples and links do not qualify. Record why each rejected lead failed.
6. **Compare identities and coverage.** Use site plus page ID where available to follow moves, recording titles and redirects; keep distinct operative sections even on the same page. When matching a reference catalogue, compare the exact page *and relevant section*, not merely a broad subject or Wikidata item. Catalogue membership is a separate dimension from local status. Recheck candidate identity and catalogue coverage before delivery.

## Request discipline and stopping rules

For Wikimedia HTTP requests, follow the [Foundation User-Agent policy](https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_User-Agent_Policy) and [API usage guidelines](https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_API_Usage_Guidelines): identify the tool and provide usable contact information. Keep per-site and overall request counts and bounded concurrency; honor `Retry-After` and pause rather than escalating after repeated rate limits. Record failed/retried checks and checkpoints. Do not use a contributor's logged-in browser, cookies or credentials to obtain authenticated access; if a site requires it, mark the site incomplete.

For each site, distinguish **enumerated**, **discovery attempted**, **candidates verified**, and **partial/failed**, with reasons and actual request counts. An interrupted scan is partial, never a completed negative result. If a query is shortened to meet search limits, results are capped, or a shard stops early, record what was omitted and mark the affected coverage partial until it is recovered. Even when all sites have been contacted, avoid claiming exhaustive discovery unless the stated search routes plausibly cover the requested class; state limitations. Failed page retrieval cannot become a removal or repeal. Preserve the last accepted complete baseline until a complete, checked replacement is accepted.

## Review gate

Before sharing, ensure every headline item has a direct local-page link, status evidence and operative wording; substantive changes have previous/current revision or diff evidence; the catalogue was checked for exact-page/section matches; false-positive discussions and redirects were resolved; and family-by-family coverage is reported. Put uncertain translations, unresolved status and failed checks in a separate review list, not the verified main findings. Write reports directly in the active worktree's `reports/` directory, including work in progress; keep raw collection output ignored as directed by the repository's `AGENTS.md`.
